# 書目同步與內容分級基礎

這一階段只建立資料層能力，不公開任何同步寫入 API。後續的本機 BAT、雲端比較與歷史回填會以這些欄位為共同協定。

## 內容分級

`books.content_rating` 使用固定值：

- `unknown`：尚未取得可靠分級
- `general`：普遍級
- `protected_6`：保護級／6+
- `guidance_12`：輔12級／12+
- `guidance_15`：輔15級／15+
- `restricted_18`：限制級／18+

另外保存出版社原文 `rating_raw`、判定來源 `rating_source` 與 0–100 的 `rating_confidence`。目前只正規化出版社明確標示，不會單靠書名關鍵字直接判成限制級。

管理員人工確認時會設定 `rating_locked = TRUE`。後續爬蟲仍可更新書名、ISBN、日期等資料，但不能覆蓋已鎖定的分級。

## 書目變更序號

`catalog_changes.id` 是每個資料庫各自遞增的書目變更游標。新增書籍、內容更新及人工分級都會新增一筆事件；單純再次看到完全相同的商品不會製造事件。

`change_origin` 用來避免未來雙向同步形成循環：

- `crawler`：這個資料庫自己的爬蟲
- `cloud_pull`：本機從雲端下載
- `sync_upload`：雲端接收本機上傳
- `manual`：管理員人工修改

第一次同步仍需要完整書目快照；完成後才使用 `catalog_changes` 增量同步。舊資料不會為了建立變更表而一次產生九千多筆事件。

## 同步游標

`catalog_sync_state` 以 `peer_code` 保存每個同步對象的：

- 最後下載的遠端變更序號
- 最後上傳的本機變更序號
- 最後驗證與成功時間
- 最後錯誤

帳號、Session、訂選清單與通知設定不屬於書目同步範圍。

本機單使用者版本和雲端多使用者版本的個人資料表結構不同，因此後續同步必須走獨立書目 API；不能用雲端 repository 直接覆寫本機的帳號／系列追蹤表。

## 相容性

`ensure_schema()` 會為既有 MySQL／TiDB 的 `books` 表補上欄位與索引；新安裝則直接從 `schema.sql` 建立完整結構。TiDB 區域搬移工具也會依外鍵順序複製兩張新增表。
