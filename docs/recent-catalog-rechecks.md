# 近期新書防漏複查（PR51）

目的：已有底庫後，補強每日增量可能漏掉的新商品；不是歷史擴充、不是每次往更舊頁面接續。

## 執行方式

每日原有五家更新、商品日期回查及分級補查保留。其後新增近期防漏工作，完成後才整理通知。

每家以台北日期計算：上次擴大掃描成功滿四個日曆日，再從第一頁重掃。第一次啟用立即符合條件；失敗不推進成功日期，下次排程可再嘗試。每家分開保存狀態，不因另一家失敗而取消其他家的週期。

| 出版社 | 每四天擴大範圍 |
| --- | --- |
| 青文 | 漫畫、小說近期清單各最多 15 頁，沿用一年日期窗口 |
| 角川 | 漫畫、小說各最多 15 頁；即將上市仍由原每日流程負責 |
| 東立 | 漫畫、小說新書列表各最多 15 頁 |
| 東販 | 新書同一分類的官方分頁連結，最多 15 頁；不切換到全歷史目錄 |
| 尖端 | 最新 200 個 sitemap 商品 ID（按數字排序），不是虛構的 15 個 HTML 頁面 |

先比對已存在的官方商品 URL，再把未收錄商品存入資料庫佇列；不為每個既有商品新增詳情請求。相同網址的 HTTP/HTTPS、追蹤參數、尖端 v2/非 v2 等格式正規化後去重。官方商品仍交給原解析器與 `upsert_book`，沿用來源整併、日期優先及人工分級鎖定規則，不修改私人書架或帳號。

## 待補抓／失敗重試

- 每家每天新增補抓額度最多 5 次，五家合計最多 25 次；資料庫原子認領，手動重跑也不能突破當天額度。
- 補查佇列與日期／分級回查額度獨立；5 本是額外工作上限，不是把原本每日新書更新縮成 5 本。
- 既有到期佇列先處理，再掃近期清單，剩餘額度可處理當天新發現商品。避免慢清單掃描阻塞既有重試。
- 每家每輪約 4 分鐘軟時間預算；請求間隔至少約 0.6 秒（清單）／1 秒（補抓）。新清單和商品請求單次逾時 20 秒、不在原地反覆重試，失敗留待下次；尖端 sitemap 沿用既有下載器的有限重試。
- 失敗保留網址、來源、種子書目、錯誤、次數及下次時間，依失敗次數退避 1／2／4／7 天，之後維持 7 天。不能將 404 或缺屬性當成已更新成功。
- 程序中止時，已入列資料不消失；商品認領一小時後可再認領。書目寫入成功才確認佇列，確認失敗則可安全冪等重做。
- 每日原爬蟲抓商品失敗也會入列；正常增量之後成功抓取並保存，可確認對應佇列，不重複補抓。僅有列表資料不能把失敗詳情視為完成。
- 非漫畫／輕小說由原商品解析器辨識後標為忽略，和網路失敗分開；未知分級仍為未知，不推測 BL 或 R18。
- 清單第一頁沒有解析到任何商品時視為失敗，不誤報整家已完成；中途失敗保留此前已入列商品與掃描頁數。

不讀寫歷史回填 checkpoint、不走到第 16 頁；每次擴大掃描都重新核對近期範圍。待補抓商品可以超過 15 頁之外繼續重試，因為它已在近期清單中被發現，這不是向後擴充歷史資料。

## 狀態與驗收

排程 JSON 新增 `recent_recheck`：各家的掃描狀態、頁數、新入列數、今日補抓、插入／更新／忽略數、待處理、失敗及最久等待天數。錯誤或等待滿 7 天會納入既有管理者 Discord 狀態警示。一般每日更新 `partial` 或補查警示在通知處理之後使 Actions 回報失敗，不再以綠燈掩蓋部分失敗。

GitHub Actions 的 `test_recent_recheck_only` 可單獨執行同樣限額的防漏工作，不執行原完整每日更新、不寄通知。不要用它繞過當天額度。既有配置環境下，`python -m app.recent_recheck --status` 僅讀取狀態，不爬網頁、不寄通知；一般入口 `python -m app.recent_recheck` 會補建表並執行有上限的工作。

新增兩張可重複建立的運作表：`catalog_recent_scans`、`catalog_product_retries`。不變動 `books` 或私人資料結構；網站及 Actions 啟動時沿用既有 `ensure_schema` 建立。這些是雲端排程運作狀態，不加入書目同步給本機，避免本機操作消耗雲端額度。

限制：固定 15 頁／200 商品只是更大的近期安全窗口，不能保證任意停機天數或任意大量上架都零漏網。積壓超過每天 5 本的處理速度時會延後，應根據積壓警示調整，而不是偷偷取消免費額度保護。
